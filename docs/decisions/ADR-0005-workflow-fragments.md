# ADR-0005：工作流的验证粒度从「整张图」改为「片段 + 组合规则」

## 背景

每一镜的 workflow 现在只能从三份固定的完整基线（`minimax_h3/t2v`、`i2v`、
`r2v`）里挑一份，逐镜头能变的只有 `positive` / `seed` / `width` / `height` /
`length_frames` / `fps`。

这个设计在「先把全流程跑通」那个阶段是对的。但真实镜头之间的差异**不是参数
差异，是图结构差异**：

| 镜头 | 需要的图 |
|---|---|
| 1 秒空镜 | 骨架 + image head + 1 张图 |
| 接上一镜的对话镜 | 骨架 + reference head + 若干参考 + AddGuide 挂上一镜末 22 帧和音频 |
| 群戏 | 骨架 + reference head + 5 张角色卡 + 2 张场景卡 + 1 段锚视频 |

节点数量和连线都不同。

`_studio.bindings` 的形状是「参数名 → 固定路径数组」：

```jsonc
"positive": ["h3_ref.inputs.prompt"]
```

它能表达「把一个值写到 N 个固定位置」，表达不了「挂 K 个槽位，K 由内容决定」。
**这是格式本身的天花板，不是少写了一行绑定。**

issue #12 讨论出的三条结论全部撞在这堵墙上：R2V 官方支持 9 图 + 3 视频 +
3 音频且每镜挂几个是变的；`MiniMaxH3AddGuide` 的节点数量等于锚点数量、可链式；
卡片的累积锁定要挂 1–10 张参考且数量随视图序号递增。

## 决策

**基线从「三张完整的图」降级为「片段库」，每一镜的节点图由确定性代码按
Agent 提交的结构化声明现场组装。**

连带地，`assets/workflows/README.md` 那条「这里放**真机跑通过**的 ComfyUI API
格式节点图」的规约，改为 **「每份文件都要能追溯到一次真机跑通的记录」**：

- 整图基线靠自己的 `bindings_verified` 与 run_id
- 片段靠 `from` + `source_run` 指回它被切出来的那份已验证基线

验证精神不丢，只是粒度从「整张图」变成「片段 + 组合规则」。

分三层，各管一段：

| 层 | 负责什么 |
|---|---|
| Skill / doctrine | 教 Agent 怎么判断：这一镜要不要接上一镜、挂哪几张卡、guide 落哪一帧 |
| `prompt_pack` schema | 约束声明的形状与取值：head 枚举、参考上限、帧网格 |
| Rust 组装器 | 声明 → 节点图。确定性、零 I/O、可单测 |

**动态性一点没少，但它被挪到了正确的位置。**

## 为什么不让 LLM 直接生成节点图

这是本 ADR 最需要说清楚的一条，因为「让模型自己拼图」看上去更灵活。

### 一、静默错接正好是这个项目最怕的失败

ComfyUI 的 API 格式是 `{node_id: {class_type, inputs}}`，连线写成
`["node_id", output_index]`。模型生成这种图的错误分两类：

- **会报错的**：引用不存在的 `class_type`、权重名拼错 → 提交时就挡下了，可接受
- **不报错的**：`output_index` 连错、VAE 接到该接 CLIP 的位置、采样器参数组合
  不合法 → **跑得通，产出错的画面**

第二类是致命的。`workflow.rs` 里 `require_verified()` 的注释写的就是这件事：
「绑错节点会静默产出错的画面，比直接报错难查得多」。PR #11 花了一整个批次
消灭「写了会被静默丢弃」，如果这里引入「连错了会静默产出错画面」，等于把刚
堵上的洞在更深的地方重新挖开。

### 二、一个真实的实例：我自己就差点犯

写真机探针时，我按「AV latent 有视频和音频两路」推断
`decode_audio.samples` 应该接 `["sampler", 1]`。

**错了。** 真实基线接的是 `["sampler", 0]`——MiniMax H3 的 AV latent 是嵌套
结构，`VAEDecodeAudio` 自己从里面取音频部分。

两边的接口类型都是 `LATENT`，**类型系统挡不住这个错**。如果不是对着已验证
基线逐字抄，这就是一次典型的静默错接：图能跑、不报错、出片，只是音频是错的。

一个 LLM 面对同样的接口签名，会犯同样的错，而且没有「对着基线抄」这个动作
可以救它。

### 三、还有一类经验根本不在文档里

把现有 i2v 与 r2v 两份基线逐节点对比，8 个骨架节点逐字相同，差异集中在几处，
其中一处是：

```
i2v:  scheduler.scheduler = "simple"
r2v:  scheduler.scheduler = "beta"
```

**R2V 配 `beta`、I2V 配 `simple`，这是真机跑出来的经验，不写在任何官方文档里。**
模型不可能知道这条，它会给两个 head 都配 `simple`，图照跑、不报错、出片，
只是质量悄悄劣化，而且没人会想到去查调度器。

这类「跟着 head 走的配套约束」在真实模型里只会更多。**它们是模型契约，不是
创作决策**，属于代码该写死的东西。

### 四、控制面调 LLM 违反分层，且不可复现

`studio-core` 的硬约束是零 I/O，整个控制面是确定性的。渲染路径上插一次 LLM
调用会带来：同一份 `prompt_pack` 两次渲染可能得到不同的图，于是
`studio.retry_stage`（「执行失败但内容没问题，原样重跑」）失去意义；多一个
网络依赖和 API key，多一类失败模式。

## 动态在哪、不动态在哪

| | 谁决定 |
|---|---|
| 这一镜要不要接上一镜 | **Agent**——它读了剧本和分镜，知道叙事连续性 |
| 接的话挂 22 帧还是 39 帧 | **Agent**——它知道这一镜多长、上一镜怎么结束 |
| 挂哪几张角色卡 | **Agent** |
| AddGuide 的 latent 接 head 的第几个输出 | **代码**——模型契约 |
| R2V 要配 beta 调度器 | **代码**——真机经验 |
| 参考图上限 9 张 | **代码**——官方能力面 |

**判断是动态的，判断的产物是结构化声明，声明到图的翻译是确定性的。**
三者分开之后，动态性一点没少，但静默错接的路径被物理上消掉了。

## 后果

### 好的

- 每一镜的图结构可以随内容变化，#12 的参考绑定、AddGuide、累积锁定不再被卡住
- 组装器是纯函数，**没有 GPU 也能完整单测**——「给定这份声明应该拼出这张图」
  可以在开发环境验完
- 「跟着 head 走的配套约束」被写进片段元数据，不再依赖谁记得
- preview 可以换一套更便宜的组合（turbo LoRA + 降 steps），而不只是缩分辨率

### 要付出的

- `prompt_pack` 的 shot 形状是破坏性改动。**按模型系列分派两种形状**：
  `minimax_h3` 用 `head` + `references` + `guides`，其它系列保留 `workflow`
  字段走整图基线。诚实反映两者能力不同，代价是 schema 有两条分支
- `capability.rs` 的对账数据源要从「基线 bindings」换成「片段库 + 组合规则」
  （逻辑不变，只换数据源）
- 片段库只对 `minimax_h3` 做。`wan2_2` / `ltx2_5` / `wan_animate2` 保持整图
  基线——只有 minimax 需要可变槽位。**两种形式共存是有意的**，不是过渡态

### 边界

片段化**不是**为了让工作流「随便拼」。片段的接线必须逐字从已验证基线切出来，
组合规则写死在代码里，非法组合在提交 `prompt_pack` 时就报
`schema_violation`。可组合的只有「挂几个参考、挂几个 guide、用哪个 head」
这些**有限且可枚举**的维度。
